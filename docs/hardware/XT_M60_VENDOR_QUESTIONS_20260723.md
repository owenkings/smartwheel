# XT-M60 双雷达厂家问题清单

日期：2026-07-23
平台：NVIDIA Jetson AGX Orin 64GB、Ubuntu 22.04、ROS 2 Humble
SDK：厂家提供的 `xtsdk_py`

## 设备与网络

| 项目 | 左雷达 | 右雷达 |
| --- | --- | --- |
| 型号/序列号 | `XTM60B20250324000151` | `XTM60B20250324000134` |
| 固件 | `XTFW-RT-V2.34.2` | `XTFW-RT-V2.34.2` |
| Boot | `BT-N1066-V0.28` | `BT-N1066-V0.28` |
| 雷达 IP | `192.168.0.101` | `192.168.1.101` |
| 掩码 | `255.255.255.0` | `255.255.255.0` |
| 网关 | `192.168.0.1` | `192.168.1.1` |
| Orin 接收 IP/端口 | `192.168.0.100:7687` | `192.168.1.100:7687` |

两台雷达分别位于不同 `/24` 子网。当前程序为每台雷达创建一个独立 SDK
对象，绑定各自的 Orin 本地 IP，但使用相同 UDP 端口 7687。ROS 话题和 frame
分别为：

- 左：`/xtm60/left/points`、`xtm60_left_link`
- 右：`/xtm60/right/points`、`xtm60_right_link`

两台安装参考点横向间距约 60 cm。用户以雷达上下两个光窗总长约 37 mm 的
中点测得参考高度约 73.5 cm；此处不是已确认的 SDK 坐标原点。

## 已应用的同一份上位机配置

2026-07-23 从两台设备分别导出的 Windows 上位机文件名为
`192.168.0.101.xtcfg` 与 `192.168.1.101.xtcfg`。两份文件内容完全相同，
SHA-256 均为：
`15D7C4A05F810F3AC74CFD10CD96E0CB50068BEA3951C9FC066DCAB743F4F6D7`。

两台均已写入并回读 SDK 当前支持的相同参数：

- 图像类型：`4`
- HDR：`1`
- 灰度积分：`2000 us`
- 四组积分时间：`1600 / 200 / 20 / 1600 us`
- 最小幅值：`70`
- 最大帧率：`10 Hz`
- 中值滤波：`3`
- Kalman：`0.30 / 300`，range 参数 `2000`
- edge：`150`
- dust：`9000 / 2`
- post-process：`5 / 1 / 9`
- reflective：`0.5 / 2.0`

右雷达应用前第三组积分时间为 `30 us`，应用后已确认变为 `20 us`，与左雷达
一致。两台的配置写入和回读检查均通过。

## 双路同时运行结果

首选的“每台雷达一个独立 SDK 对象/独立进程”方案已复测通过，因此没有再测试
“一个 SDK 对象同时管理两个 IP”。两个独立配置进程同时运行约 9.9 秒，分别
收到左 39 帧、右 40 帧，退出码均为 0；随后两个生产 ROS 节点并发 60 秒，
两台均持续输出有序 `160 x 60` 点云，每帧 9,600 点：

| 指标 | 左雷达 | 右雷达 |
| --- | ---: | ---: |
| 消息数 | `599` | `600` |
| 接收频率 | `9.973 Hz` | `9.984 Hz` |
| header 频率 | `9.974 Hz` | `9.984 Hz` |
| 有限点比例 | `78.960%` | `71.115%` |
| 最大强度 | `2121` | `2347` |
| 时间戳倒退 | 0 | 0 |
| 发布为有限点的 `>=64000` 无效值 | 0 | 0 |

资料写明正常幅值范围是 `0-2039`、`>=64000` 是无效像素，但没有解释
`2040-63999`。此前主要由右雷达复现 `2154-2165`；新导出配置与当前场景下
左雷达也达到 `2121`，右雷达达到 `2347`，因此问题不是右雷达独有，也不能
归因于右雷达原来的第三积分时间 `30 us`。

当前两台“能同时运行”只证明 SDK/网络并发共存，不证明两帧在同一时刻曝光，
也不证明点云已经硬件同步。SDK 设备信息显示两台均为 `timeSyncType=0`、
`ptpdomain=0`。SDK 帧时间戳在单机内递增，但不是 Unix 时间；当前 ROS 验收
使用 Orin 主机收帧时间，不能据此证明左右雷达对时。

## 请厂家明确答复的问题

1. 当前已验证**每台雷达各创建一个 SDK 实例/独立进程**可以稳定并发约
   10 Hz。请确认这是否就是客服所说的“把 SDK 实例化一份”，并提供官方双
   XT-M60 最小示例。
2. 这里的“同步进行”只表示两台并发采集，还是保证同一时刻曝光/同一帧号？
   XT-M60 是否支持硬件触发、同步线、PTP 或其他跨设备时间同步？
3. 若支持 PTP，请给出 `timeSyncType`、`ptpdomain` 的合法值、设置 API、网络
   拓扑、主时钟要求和验证同步误差的方法；若支持同步线，请给出接口针脚、
   电气参数、主从配置和触发时序。
4. SDK 帧时间戳的单位、起点、回零条件是什么？它表示曝光开始、曝光结束、
   雷达内部出帧，还是 UDP 到达 SDK 的时间？两台设备的时间戳是否可以直接
   相减？断电、重启测量或 SDK 重连会怎样变化？
5. 两台雷达在相同配置下均可出现 `>2039` 幅值，本次左 `2121`、右 `2347`。
   这些值的正式语义是什么？
   它们是有效的 HDR/反射滤波输出、饱和值、固件缩放、需要标定的异常，还是
   应按无效点处理？是否与场景强反射/HDR 有关，或需要厂家标定、升级固件？
6. 新导出包含 `freq1..5 = 0,0,0,3,2`，与官方示例固定传入第五个枚举 `2`
   一致。请确认当前 SDK 调用 `0,0,0,3,2` 的正式含义和单位。
7. 上位机导出的 spatial filter 字段在当前官方 Python 示例/API 中没有对应
   调用。请提供该滤波器的正式 API、参数单位和调用顺序，或确认 XT-M60
   Python SDK 不支持它。
8. 请给出 `xtsdk_py` 在“双实例 + ROS 2”情况下的官方安全停止、释放和析构
   顺序。应用侧已避免 SIGINT 后重复析构导致的段错误，但需要确认官方推荐的
   `stop/shutdown/destroy` 顺序及线程退出条件。
9. 请明确 SDK 点云坐标系的原点位置和 XYZ 正方向。手册可确认下光窗为 VCSEL
   发射、上光窗为接收，但未确认点云坐标原点位于哪个光窗、两光窗中点、机壳
   基准面还是内部成像器件；这会直接影响双雷达外参。
