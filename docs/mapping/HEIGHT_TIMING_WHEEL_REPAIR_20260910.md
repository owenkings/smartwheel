## 3. 双雷达时间问题：修复软件拼接，但不冒充硬件同步

旧 `dual_lidar_cloud_fusion_node.py` 把左右点云分别变换到各自采样时刻的 `base_link`，然后直接拼接，并给合并云标上较新的时间。这在车体运动时将两个不同瞬间的坐标混为一谈。

新增可选运动补偿：通过连续局部里程计参考系，将两个时刻的数据变换到同一目标时刻后再拼接；正式启动路径明确开启，旧通用入口默认兼容关闭。FAST-LIO 路径采用 `camera_init`，不使用可能受回环跳变影响的 `map` 进行帧间补偿。

- 使用对应时刻的 TF，不伪造雷达采样时间；保持原始 intensity。
- 过期、超前、非递增、超过时间差限制的数据被拒绝。
- 缺失准确时刻 TF 时短时有界等待，不偷用最新 TF 拼接；已消费帧不重复使用。
- 正式外参/时间来源 APPROVED 门禁及 `20 ms` 配对上限不变。

50 ms 错开发射有光学 ToF 串扰缓解目的，不能简单改为同时发射。软件补偿只能处理已知时间和自车运动，不能解决光学串扰、未知采样延迟、H30 缺设备时间戳或运动物体。**目前不能说双雷达已经同步，也没有开启未经批准的正式双雷达建图。**

详见同树 `docs/mapping/DUAL_LIDAR_TIME_COMPENSATION_20260910.md`；测试覆盖 50 ms 平移、旋转、真实 tf2 Buffer、时间异常、TF 延迟等待和 XYZI 保留。

## 4. 轮速里程计：真正接入 FAST-LIO，而非只显示对照输出

此前配置还存在一个确定错误：launch 节点名为 `wheel_imu_ekf`，引用的参数 YAML 顶层名却是 `ekf_filter_node`。新增同名配置 `right_diag_wheel_imu_ekf.yaml` 后，独立 EKF 只融合电机测得的前向速度与 IMU 的 z 轴角速度，不重复融合由相同编码器积分得出的 x/y/yaw。

运行参数查询确认 `/wheel/odom`、`/imu/data`、`publish_tf=false` 已实际加载；`/odometry/filtered` 仍只是对照输出，不竞争 FAST-LIO 的 TF，也不作为重复相关的 IMU 观测再喂回 FAST-LIO。

真正的轮速接入位于 FAST-LIO `src/laserMapping.cpp` 和新增 `include/wheel_velocity_update.hpp`：

- 从 `/wheel/odom` 使用电机反馈速度，从 `/base/wheel_feedback_healthy` 确认反馈健康；不是从按键或速度指令冒充真实运动。
- 根据 base/IMU 外参和角速度补偿旋转杠杆臂，加入前向速度观测。
- 新鲜度、协方差、速度界限、创新/NIS、修正幅度均有检查；健康过期、重复、未来或陈旧样本不参与。
- 只直接修正速度，保留完整观测雅可比并使用 Joseph 协方差更新；不硬覆盖位置、姿态、重力或外参。
- 静止 ZUPT 已更新时不重复消费同一轮速信息；LiDAR 更新失败时不绕过定位质量门。
- 默认功能关闭，仅当前诊断入口明确开启。姿态/旋转仍依赖 IMU+LiDAR，不是“编码器轨迹永远正确”的纯轮式定位。

轮径、轮距、驱动反馈缩放、打滑和动态时间偏差仍可导致误差；软件接入不等于这些实车参数已校准。持续被拒绝的 LiDAR 更新也不会仅靠此轮速观测自动恢复。

## 7. 离线回放暴露的 FAST-LIO 同步队列永久阻塞

**确定代码错误：**`laserMapping.cpp::sync_packages()` 在 `meas.imu.empty()` 时直接 `return false`，却既不移除队首点云，也不清除 `lidar_pushed`。如果最早点云早于现有全部 IMU，后续更晚 IMU 永远不能补齐过去；此帧永久堵住整个队列。

真实记录证据：

- 首点云 header：`1788528816.5019486 s`。
- 首 IMU header：`1788528816.5782652 s`；相差 **76.3166 ms**。
- 修复前带时钟审计的 45 秒回放：445 帧适配点云、8,876 条 IMU、2,221 条 wheel/health、4,445 条 clock，**0 帧里程计**。
- 对应证据 `auto_test/wheel_aiding_replay_20260910_121254/result.json`。这是可复现的一种启动/重连/切片回放冻结机制，不能据此追认用户之前每次冻结都由同一原因引起。

修复逻辑：确认 IMU 时间已经覆盖点云结束时刻后，消费当前点云；若不存在可匹配的过去 IMU，则丢弃这帧无法使用的点云，保留未来 IMU 给下一帧。另将结束时间恰好相等的 IMU 纳入匹配。仍然缺少后续 IMU 覆盖时继续等待，不放宽真实同步或初始化质量条件。

本次新增 `test_fastlio_sync_queue.py`，提取当前实际 C++ 函数并用最小队列/消息替身编译执行；四种场景全部通过：首帧缺 IMU 丢弃、后续帧推进、恰好相等时间戳接受、缺末端 IMU 时保持等待。没有复制一个不同的 Python 实现来代替生产函数。再次编译后同一真实运动切片的结果见后续记录，不用数学单测冒充动态回放通过。
